## 1. 引言

### 1.1 背景与问题

机场地面服务低效造成的航班延误占国内大型机场所有延误的 15.45%，欧美国家占比达 25%。现有场面监视系统（SMR、MLAT、ADS-B）主要解决"车辆在哪"的监视问题，而调度仍依赖人工经验，导致车辆利用率低、空驶等待多、任务衔接差。

### 1.2 系统核心定位

> **本系统的价值不在于界面有多好看、功能有多丰富，而在于是否把机场地面服务的业务逻辑分析透彻，并正确地映射到面向对象的模型设计中。**

具体来说，本系统的核心工作分为三个层面：

1. **调研层** — 梳理机场地面服务的真实业务流程：一架飞机落地后到起飞前，到底有哪些车辆需要服务它们？顺序是什么？每类车有什么作业特点？
2. **建模层** — 将调研结果用 OO 分析和数据模型准确地表达出来，尤其是各类车辆的差异化属性（适配机型、服务模式、作业时长等），以及任务之间的时序依赖关系。
3. **系统层** — 基于上述模型实现最简可行的调度逻辑，验证模型的正确性。

界面展示、前端复杂度、功能数量**不是本阶段的重点**。

### 1.3 设计原则（结合 MIS 系统设计理论）

- **业务驱动** — 所有功能设计来源于对真实机场业务流程的调研，而非凭空想象。
- **面向对象分析** — 对每种车辆类型进行独立分析，提炼其属性、行为与约束，确保模型与物理世界一致。
- **系统性** — 统一代码规范、模块化设计，确保数据全局共享。
- **可靠性** — 具备异常检测与人工兜底机制，故障时不影响既有安全系统。
- **经济性** — 基于模拟数据进行原型验证，避免真实环境高昂试错成本。

## 2. 业务调研 — 机场地面服务车辆分析

> 这是本系统的核心内容。以下分析基于对机场地面保障流程的调研，重点描述每种车辆的属性差异、作业特点和调度约束。

### 2.1 车辆分析维度

机场地面服务车辆种类繁多，不同车型在以下维度上存在显著差异：

| 维度 | 说明 | 调度意义 |
|------|------|---------|
| **服务模式** | 一对一（一次只能服务一架飞机）vs 一对多（可串飞多架） | 决定任务能否并发分配 |
| **适配机型** | 是否能服务大型机（如 B777、A380） | 机型不对口分配了也做不了 |
| **作业时长** | 完成一次保障的标准时间（因机型而异） | 影响调度时间窗计算 |
| **满载/空载约束** | 是否需要回补才能执行下一任务（如加油车油量、行李车舱位） | 决定任务间是否需要插入回补行程 |
| **前置依赖** | 该任务开始前必须已完成哪些其他任务 | 决定任务执行顺序 |
| **占用时长类型** | 短时占用（如客梯车对接几分钟）vs 长时占用（如电源车全程连接） | 影响车辆可用性判断 |

### 2.2 各类车辆详细分析

#### FUEL — 加油车

| 属性 | 说明 |
|------|------|
| 服务模式 | **一对一**。加油车必须全程停靠飞机旁，无法同时服务多架飞机。 |
| 适配机型 | 大型机（B777/B787/A330 等）需要大容量油车，小型机（A320/B737）可用标准油车。（注：本系统 v1 暂时简化为一车通用，后续可按油量分级） |
| 作业时长 | A320/B737 约 15-20 分钟；B777/B787 约 30-40 分钟 |
| 满载约束 | 油量耗尽后必须返回油库补充，补充时间约 10 分钟 |
| 前置依赖 | 无严格依赖，通常可与行李装卸并行进行 |
| 特殊说明 | **安全优先级最高**，加油期间附近区域禁止明火作业 |

#### BAG — 行李车

| 属性 | 说明 |
|------|------|
| 服务模式 | **一对多**。行李车可在多个航班之间串行作业（卸完 A 航班的行李 → 送往行李分拣区 → 再去 B 航班装行李）。 |
| 适配机型 | 通用 |
| 作业时长 | 卸货约 10-15 分钟，装货约 15-20 分钟（与旅客人数正相关） |
| 满载约束 | 车厢满后需先前往行李分拣区卸空 |
| 前置依赖 | **到达航班**：必须等客梯车到位、旅客下机后才能开始卸行李；**出发航班**：必须在旅客值机之后、关舱门之前完成 |
| 特殊说明 | 同一辆行李车可在相邻时间段服务多个航班，调度灵活性最高 |

#### TOW — 牵引车（推车）

| 属性 | 说明 |
|------|------|
| 服务模式 | **一对一**。牵引车推出飞机期间必须全程连接，无法中断。 |
| 适配机型 | 大型机需要大推力牵引车（如 B777 需要 60 吨级），小型机可用标准牵引车 |
| 作业时长 | 连接 + 推出 + 脱钩约 8-12 分钟 |
| 前置依赖 | **必须最后执行**。推出前所有其他保障车辆必须撤离、舱门关闭、廊桥收回 |
| 特殊说明 | 牵引车是**离港流程的最后一步**，它的完成时间就是飞机可以滑出的时间 |

#### STAIR — 客梯车

| 属性 | 说明 |
|------|------|
| 服务模式 | **一对一**。客梯车对接舱门期间无法移动。 |
| 适配机型 | **机型敏感**。B737/A320 等单通道飞机使用标准客梯；B777/B787 等双通道飞机需要更高/带廊桥适配的客梯；A380 需要专用三层客梯。 |
| 作业时长 | 到位对接约 3 分钟，撤离约 2 分钟 |
| 前置依赖 | **到达**：客梯车必须先于旅客下机前到位；**出发**：必须在旅客登机结束后、关舱门前撤离 |
| 特殊说明 | 高度与机型必须匹配，否则无法对接舱门 |

#### BUS — 摆渡车

| 属性 | 说明 |
|------|------|
| 服务模式 | **一对一（严格）**。一辆摆渡车一次只能运输一个航班的旅客，不能混装不同航班的旅客。这是最关键的业务约束。 |
| 载客量 | 小型约 50 人，大型约 120 人。需要根据航班旅客人数派对应容量的车。 |
| 适配机型 | 按载客量而非机型区分。B777（约 300 人）可能需要 3-4 辆摆渡车循环运输。 |
| 作业时长 | 机位到航站楼单程约 5-10 分钟 |
| 前置依赖 | 必须在客梯车到位、旅客开始下机后使用 |

#### GPU — 地面电源车 / ACU — 空调车

| 属性 | 说明 |
|------|------|
| 服务模式 | 一对一。连接飞机期间固定不动。 |
| 作业时长 | 全程连接（从飞机到位到推出前），属于**长时占用型**车辆 |
| 前置依赖 | 飞机到位后即可连接，推出前才断开 |

### 2.3 任务依赖关系（保障流程顺序）

航班地面保障不是所有任务同时进行的，而是有明确的时间先后关系。以下是一个典型航班的保障流程时序：

```
时间轴 →

  飞机着陆 / 到位
       │
   ├── GPU / ACU 接入 ─────────────── 全程占用，最早接入最晚断开
       │
   ├── 客梯车到位 ────────────────── 到达流第一步
       │
   ├── 旅客下机（摆渡车循环运输） ──── 依赖客梯车到位
       │
   ├── 行李卸货 ───────────────────── 依赖客梯车到位（旅客先下）
       │
   ├── 清洁 / 加水 / 排污 ────────── 过站服务
       │
   ├── 加油 ──────────────────────── 可与行李装卸并行
       │
   ├── 行李装货
       │
   ├── 旅客登机（摆渡车循环运输） ──── 出发流
       │
   ├── 客梯车撤离 ──────────────────
       │
   ├── GPU / ACU 断开
       │
   └── 牵引车推出 ────────────────── 离港最后一步
```

**关键依赖关系总结**：

| 依赖 | 说明 |
|------|------|
| 客梯车 → 旅客上下机 → 行李装卸 | 旅客流有严格先后 |
| 所有车辆撤离 → 牵引车推出 | 牵引车是最后一步 |
| 加油 与 行李装卸 可并行 | 无依赖关系 |
| GPU/ACU 全程在位 | 最早接入、最晚断开 |

## 3. 面向对象模型

### 3.1 核心思想

本系统以 **Vehicle（车辆）** 为核心对象，通过 OO 分析将每种车辆的差异化属性封装到对象中。调度算法的输入不是"一堆叫不同名字的车"，而是"带有不同行为约束的业务对象"。

### 3.2 类设计

```
┌──────────────────────────────────┐
│            Vehicle               │
│──────────────────────────────────│
│ plate: str                       │
│ type: str (FUEL/BAG/TOW/...)     │
│ status: IDLE/BUSY/MAINTENANCE    │
│ region_id: FK                    │
│ attributes: JSON                 │  ← 差异化属性字典
│   ├── service_mode               │     "ONE_TO_ONE" / "ONE_TO_MANY"
│   ├── compatible_aircraft[]      │     适配机型列表
│   ├── base_duration_min          │     标准作业时长
│   └── capacity                   │     容量（载客/载油/载货量）
│──────────────────────────────────│
│ can_service(aircraft_type): bool │  机型适配检查
│ is_available(): bool             │  可用性判断
└──────────────────────────────────┘
```

**实际数据举例**：

```python
# 摆渡车 — 严格一对一，不可混装航班
Vehicle(plate="京A-BUS01", type="BUS",
    attributes={
        "service_mode": "ONE_TO_ONE",
        "passenger_capacity": 120,
        "base_duration_min": 15
    })

# 行李车 — 可串飞，灵活性最高
Vehicle(plate="京A-BAG01", type="BAG",
    attributes={
        "service_mode": "ONE_TO_MANY",
        "baggage_capacity": 50,
        "base_duration_min": 15
    })

# 客梯车 — 机型敏感，高度是关键参数
Vehicle(plate="京A-STAIR01", type="STAIR",
    attributes={
        "service_mode": "ONE_TO_ONE",
        "max_height_m": 5.5,
        "compatible_aircraft": ["A320", "B737"],
        "base_duration_min": 5
    })
```

### 3.3 Aircraft_Resource — 飞机资源需求规则

这是连接"航班"和"任务生成"的核心业务规则表。它记录了**每种机型需要什么类型的车、多少辆**，是调研成果的集中体现。

| 机型 | 所需车辆类型 | 数量 | 备注 |
|------|-------------|------|------|
| A320 | FUEL | 1 | 标准加油车 |
| A320 | BAG | 2 | 一卸一装，或一辆串行 |
| A320 | TOW | 1 | 标准牵引车 |
| A320 | STAIR | 1 | 标准客梯 |
| A320 | GPU | 1 | 全程连接 |
| A320 | BUS | 1-2 | 视旅客人数而定 |
| B777 | FUEL | 1 | 大容量油车，加油时间更长 |
| B777 | BAG | 3 | 旅客多，行李量大 |
| B777 | TOW | 1 | 大推力牵引车 |
| B777 | STAIR | 2 | 双通道，需两个客梯 |
| B777 | BUS | 3-4 | 约 300 人需多车循环 |

### 3.4 调度算法约束

调度算法在分配车辆时，按以下优先级检查业务约束：

1. **机型适配** — 该车是否能服务此机型？（如客梯车高度是否匹配）
2. **服务模式** — 该车是否已被其他任务占用？（ONE_TO_ONE 的车同一时间只能分配一个任务）
3. **区域匹配** — 优先分配同区域车辆，减少空驶
4. **任务依赖** — 该任务的前置任务是否已完成？（如牵引车必须在其他所有任务完成后才能开始）
5. **满载约束** — 该车是否需要回补后才能继续执行？（如加油车油量不足）

## 4. 数据模型

### 4.1 E-R 模型

```
Flight (1) ──────── (N) Task        一个航班生成多个任务
Vehicle (1) ──────── (N) Task       当前简化为一对一分配
Region (1) ──────── (N) Vehicle     区域与车辆
Region (1) ──────── (N) Flight      区域与航班
Aircraft_Resource                   独立规则表
```

> **注**：设计文档原案中 Task-Vehicle 为多对多关系（通过中间表），当前版本实现为一对多（一个任务分配给一辆车）。多车协同作业（如多辆摆渡车服务一个航班）通过生成多个同类型任务实现。后续可根据需要引入中间表。

### 4.2 核心表设计

**Flight（航班）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | Integer PK | 主键 |
| flight_no | String(16) | 航班号，如 CA1234 |
| airline | String(32) | 航空公司 |
| aircraft_type | String(10) | **机型**（如 A320/B777），用于匹配 Aircraft_Resource 规则 |
| scheduled_at | DateTime | 计划时间 |
| gate | String(8) | 登机口/停机位 |
| region_id | FK | 所在区域 |
| status | String(16) | SCHEDULED / ARRIVED / DEPARTED / CANCELLED |

**Vehicle（车辆）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | Integer PK | 主键 |
| plate | String(16) | 车牌号 |
| type | String(8) | FUEL / BAG / TOW / STAIR / BUS / GPU ... |
| status | String(16) | IDLE / BUSY / MAINTENANCE |
| region_id | FK | 当前所在区域 |
| attributes | JSON | **差异化属性字典**（见 2.2 节分析） |

**Task（任务）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | Integer PK | 主键 |
| flight_id | FK | 关联航班 |
| vehicle_id | FK | 分配的车辆（可空） |
| task_type | String(8) | 对应车辆类型 |
| scheduled_start / end | DateTime | 计划起止时间 |
| status | String(16) | PENDING / IN_PROGRESS / COMPLETED / FAILED |
| depends_on | Integer | **前置任务 ID**（可空，用于表达任务依赖链） |

**Aircraft_Resource（飞机资源需求规则）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | Integer PK | 主键 |
| aircraft_type | String(10) | 机型，如 A320 |
| required_vehicle_type | String(8) | 所需车辆类型 |
| quantity | Integer | 数量 |

**Region（区域）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | Integer PK | 主键 |
| code | String(8) | 区域代码，如 A01 |
| name | String(64) | 区域名称，如"1号航站楼东侧" |

## 5. 调度核心算法逻辑

### 5.1 算法原则

1. **机型适配检查** — 确认可用车辆的属性中是否兼容目标机型
2. **区域优先** — 同区域空闲车辆优先
3. **服务模式检查** — ONE_TO_ONE 车辆不可同时分配多个任务
4. **依赖顺序执行** — 按任务依赖链依次分配

### 5.2 任务执行顺序

以典型 A320 航班保障为例，任务按以下顺序分配和执行：

```
 1. GPU 接入          (飞机到位 → 立即执行，长时占用)
 2. 客梯车到位         (无前置依赖)
 3. 摆渡车就位         (依赖客梯车到位)
 4. 行李卸货           (依赖旅客下机完成)
 5. 加油               (可与行李装卸并行)
 6. 清洁/加水/排污     (过站服务)
 7. 行李装货
 8. 摆渡车运输旅客登机  (出发流)
 9. 客梯车撤离
10. GPU 断开
11. 牵引车推出         (依赖所有其他任务完成)
```
